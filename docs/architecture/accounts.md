# sotyware accounts and end-to-end encrypted sync

Status: design accepted 2026-11-15
([ADR-032](decisions.md#adr-032-sotyware-accounts-are-a-separate-service-synced-configuration-is-end-to-end-encrypted-with-a-recovery-key-and-device-keys)).
The service (`server/`) and the desktop client (`src-tauri/src/account/`,
Account page) are implemented and tested locally (end to end, the service in
process, several device profiles). The service runs at
`https://accounts.sotyware.com` since 2026-11-17 (ADR-045), the
`PRODUCTION_SERVER` of builds from `main`, of `v0.1.2` (2026-11-17), the
first release that offers accounts, of `v0.1.3` (2026-11-19) and of `v0.1.4` (2026-11-25); `v0.1.0` and `v0.1.1` have no
service configured, and test-profile builds have none unless
`SOTYWARE_ACCOUNT_SERVER` names one. Details in [status.md](../status/status.md) and
the [journal](../status/journal.md). Threats: [threat-model.md](threat-model.md).
Operating the service: [server.md](../development/server.md).

**Key proof.** The service cannot check that a device holds the account
key without learning it, so it stores the SHA-256 of a *key proof*,
`HKDF-SHA256(AK, info = "sotyware key proof v1" ‖ account id)`, recorded
when sync is set up (and replaced on rotation). Writing the vault, storing
a device wrap, approving an enrollment and replacing the recovery wrap all
require the proof: a password alone can sign in but cannot overwrite or
re-key the vault. The proof reveals nothing about AK (one-way), and the
service stores only its hash.

**Email verification and pre-registration.** Verifying an address needs
the code *and* the password; registering an unverified address again
replaces its password and sends a new code, so someone who registered a
stranger's address first cannot keep it.

Accounts are **optional**. An installation without a sotyware account keeps
working exactly as before; nothing is sent anywhere.

## Pieces

| Piece | Where | Knows |
| --- | --- | --- |
| Account service | `server/` (Rust, axum, SQLite) | email, Argon2id password hash, devices (name, platform, public key, state), token hashes, the vault **ciphertext**, wrapped account keys, audit events |
| Desktop client | `src-tauri/src/account/` | everything above for its own account plus, in the OS credential store: refresh token, the device's X25519 private key, the unwrapped account key |
| The user | — | password, recovery key (shown once) |

The service never receives the account key, the recovery key, a device
private key or a cloud provider credential in plaintext, and holds no
credential for any bucket.

## Keys

| Key | Generated by | Stored |
| --- | --- | --- |
| **Account key** `AK` (256-bit, random) | first device, when the user sets up sync | OS credential store of each enrolled device; at the server only wrapped (below) |
| **Recovery key** `RK` (256-bit, random) | first device; shown once as 52 Crockford base32 characters in 13 groups + a 4-character checksum group; the user must retype it | only by the user |
| **Recovery wrap** | `XChaCha20-Poly1305(KEK_r, nonce, AK, aad)` with `KEK_r = HKDF-SHA256(ikm = RK, salt = "sotyware recovery v1", info = account id)` | server |
| **Device key pair** (X25519) | each device | private key in the OS credential store; public key at the server and in the vault's trusted-device list |
| **Device wrap** | sealed box (X25519 + XSalsa20-Poly1305, libsodium `crypto_box_seal` construction, crate `crypto_box`) of `{account id, key id, AK}` to the device's public key | server |

The password is used only to authenticate to the service. It never derives a
vault key: a guessed or reused password does not expose any credential.

## The vault

One JSON document, encrypted as a versioned envelope:

```json
{ "format": "sotyware-vault", "v": 1, "alg": "xchacha20poly1305",
  "kid": "<account key id>", "nonce": "<24 bytes, base64url>", "ct": "<base64url>" }
```

AAD = `sotyware-vault|v1|<account id>|<kid>`. Clients refuse any other
`format`, `v` or `alg` (no downgrade). The plaintext:

```json
{ "revision": 7, "updatedAt": "…", "updatedBy": "<device id>",
  "trustedDevices": { "<device id>": { "publicKey": "…", "name": "…", "addedBy": "…" } },
  "records": {
    "storage-account:<id>": { "rev": 3, "updatedAt": "…", "device": "…", "deleted": false,
       "data": { "config": { …AccountConfig… }, "credentials": { "accessKeyId": "…", "secretAccessKey": "…" } } },
    "favorite:<account>:<path>": { … },
    "backup-job:<id>": { … }
  } }
```

Synced: provider type, display name, region, endpoint, addressing, buckets,
transfer limit, credentials (only inside the ciphertext), favorites, backup
job definitions (source/destination by account id, schedule, retention).
Never synced: local paths, temporary files, journal entries, running
operations, SQLite internals, recent items (device-specific).

## Flows

**Register:** `POST /v1/accounts {email, password}` → always `202` with the
same body (an existing email gets a "someone tried to register" mail, a new
one a verification code). `POST /v1/accounts/verify {email, code}` activates.

**Sign in:** `POST /v1/sessions {email, password, device: {name, platform,
publicKey}}` → `{accessToken (15 min), refreshToken (30 days), deviceId,
vaultAccess: "enrolled" | "pending" | "none"}`. Wrong email and wrong password
give the same answer and take the same time (a dummy Argon2id verification
runs for unknown emails).

**Set up sync (first device):** generate AK, RK, device key pair; show RK and
require it retyped; upload recovery wrap, own device wrap and the first vault
(revision 1) containing the local storage accounts and credentials.

**Enroll another device:** after sign-in it is `pending`:
- *with the recovery key:* fetch the recovery wrap, derive `KEK_r`, unwrap AK,
  upload this device's wrap, add itself to `trustedDevices` (vault write);
- *by approval:* `POST /v1/enrollments` (its public key); an enrolled device
  lists pending requests, shows the requesting device's name, platform and a
  fingerprint (SHA-256 of `public key ‖ enrollment id`, 15 decimal digits in
  three groups) that the new device shows too; on approval it seals AK to the
  new public key (`POST /v1/enrollments/{id}/approve`) and adds the device to
  `trustedDevices`. The new device fetches the sealed key and unseals it.

**Sync:** `GET /v1/vault` → `{revision, envelope, updatedAt}`; `PUT /v1/vault
{expectedRevision, envelope}` → `200 {revision}` or `409 {revision}`. Clients
keep the last synced envelope (ciphertext) as the merge base and the highest
revision seen; they refuse a vault older than that. Three-way merge per
record: changed on one side → that side; changed on both, equal → fine;
changed on both, different → remote wins and the local version is kept as a
`conflict:<record>:<device>` record shown to the user. Deletions are
tombstones (`deleted: true`). Applying the merged vault locally adds, updates
or removes storage account configurations and their OS credential store
entries; remote objects are never touched.

**Revoke a device:** `DELETE /v1/devices/{id}` ends its sessions and deletes
its wrap, and the next sync removes it from the vault's trusted devices.
The page then offers to rotate: new AK (new `kid`), the vault re-encrypted,
the new key wrapped to the recovery key (typed, or a new one shown once)
and sealed to every remaining trusted device, all in **one transaction**
at the service (`POST /v1/keys/rotate`: recovery wrap, key proof, vault and
device wraps change together or not at all; enrolled devices not listed
must enroll again). Other devices notice the new `kid` and fetch their new
wrap. The UI says plainly that the revoked device may still hold
credentials it decrypted before and that provider keys should be rotated
at the provider.

### When sync runs

After sign-in with access, set-up, unlock, approval, approving another
device, revocation, rotation, conflict resolution and "Sync now", as
before; and, since 2026-11-15 (ADR-042), on its own for a device that is
signed in and enrolled (`src/accountSync.svelte.ts`):

- when sotyware starts, so a computer picks up what the others changed;
- when the window is focused again, at most every 15 minutes;
- after a storage account was added, changed or removed on this computer.

These are events, not a timer: there is still no background (periodic)
sync, and a window that stays unfocused does not sync. Offline, the sync
fails, Rust records why (`lastSyncError`), the sidebar's Account item shows
it (a dot and its tooltip: synced N minutes ago, not synced and why,
waiting for unlock, conflicts to review), and every storage account keeps
working locally. After a sync the shell reads the storage accounts again.
A build without a configured service (`v0.1.0`, `v0.1.1`, a test-profile
build whose run names none) only reads the local status.

**Password change / reset:** change needs the old password and revokes other
sessions; reset (`/v1/password/reset/request` → always `202`, code by mail;
`/v1/password/reset/confirm`) revokes every session and every device wrap
(devices must re-enroll with the recovery key or an approval from a device
that was not reset — after a reset none remain enrolled, so the recovery key
is required). The vault ciphertext is kept.

**Delete account:** `DELETE /v1/account {password}` removes account, devices,
tokens, wraps and vault immediately. Server backups keep them until they age
out (retention documented in server.md). Local configuration on devices is
kept (sync turns off).

**Lost everything:** without the recovery key and without any enrolled
device, the vault cannot be decrypted by anyone, including the operator. The
storage data is unaffected: re-create provider keys in the provider's
console and add the accounts again.

## Tokens and sessions

Opaque 256-bit random tokens, base64url; the service stores SHA-256 hashes
only. Access tokens: 15 minutes. Refresh tokens: 30 days, single use; each
refresh returns a new pair; presenting an already used refresh token revokes
the whole family (that device's sessions). The client keeps the refresh token
in the OS credential store and the access token in memory.

## Abuse protection

- Per-IP token bucket on every endpoint; tighter buckets on sign-in,
  registration, reset and verification.
- Per-account failure counter with progressive lockout (exponential delay
  after 5 failures, capped at 15 minutes); lockouts do not reveal whether the
  email exists (unknown emails are "locked" identically).
- Verification and reset codes: 8 digits, 15 minutes, 5 attempts.
- Request body size limit (vault ≤ 1 MiB); JSON only; no cookies (bearer
  tokens), so no CSRF surface; CORS disabled.
